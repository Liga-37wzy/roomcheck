# 范围、MVP 与需求验证

## 目标用户

第一阶段：愿意读写简单结构化文本的小型密室/桌面解谜设计者，以及独立文字冒险开发者。学习者可用原创案例理解逻辑问题。面向只会拖拽图形的非技术设计者，目前 CLI 的体验可能不合格，需要真实试用验证。

用户任务：在试玩或修改设计之前，确认能通关；发现特定顺序导致的死路；确保剧情要求的必做谜题无法被跳过；修改设计后自动重复检查。

## MVP 验收

1. 只安装 Python 即可本地运行；不需要账户、密钥、数据库或网络。
2. 实体和线上各有一个通过的模型。
3. 道具消耗、无入口依赖环、跳过必做谜题各有可复现失败案例。
4. 能显示通关路径、失败动作序列和失败时的库存。
5. 错误输入明确报错；搜索超限不能返回无条件通过。
6. README、MIT 许可、模型说明、测试和 GitHub Actions 配置齐备。

不纳入 MVP：画布编辑、登录、云端保存、协作、游戏运行时、机关控制、自动理解谜面、计时和难度估计、导入任意其他工具格式。JSON 输入不是竞品 JSON 的兼容格式。

## 尚未执行的需求验证计划

计划找 3 位实体设计者和 3 位线上解谜开发者；这是下一阶段计划，不是已完成访谈。通过公开帖子或项目作者联系都需要用户另行授权实际发送消息。

访谈先问最近一次真实修改流程：使用什么资料，出过什么逻辑问题，何时发现，修改花了多久。避免先演示产品再询问“喜不喜欢”。取得对方同意后，用匿名化的 5-15 步流程进行任务测试。

试验：参与者先用原工具检查一份流程，再用 RoomCheck 检查另一份复杂度相近且预置已知错误的流程；交换两组顺序，记录录入时间、漏报、误报、能否解释反例、修复后能否复查。合成缺陷结果和真实发现要分开报告。

暂定继续投入门槛（产品假设，不是行业标准）：至少 4/6 人能在 20 分钟内完成建模；至少 4/6 人无需作者解释就能修复反例；至少 2 人主动愿意在后续真实项目复用。若录入成本过高，优先做现有工具导入或表单；若没有实际逻辑问题，停止堆功能，重新定位。

不以 stars、AI 调用量或演示好评替代留存与实际使用证据。先作为可维护的开源学习/设计工具，不设未经验证的收入预测。

## 演进顺序

- v0.1：当前离线 CLI 与确定性检查。
- 通过试用门槛后：表单或编辑器导入，保留同一个检查核心。
- 出现真实需求后：多数量道具、可重复动作、分玩家库存。届时必须重新定义有限状态边界和测试语义。
- AI 仅作为可选录入辅助：生成的模型必须人工确认，结论仍来自检查器。

技术选择优先让普通 Python 水平开发者读懂。当前无需前后端框架、容器、消息队列或部署平台。
