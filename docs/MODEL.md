# 输入与模型语义 v1

输入是 UTF-8 JSON（允许 UTF-8 BOM），根字段见 README；根和动作对象均拒绝未知字段。重复 JSON 键也拒绝。`version` 必须是整数 1。`title` 可省略；动作 `label` 可省略。`facts`、`initial`、`goals`、`actions` 必须提供。`must_solve` 默认空列表。

事实 ID 和动作 ID 各自唯一，可以属于不同命名空间。最多 128 个事实、40 个动作；ID 最多 64 个字符。标题/标签为 1-200 个字符。`goals` 不允许为空；初始状态可以已满足目标，此时胜利路径为 `[]`。

状态 S = (当前事实集合 I, 已执行动作集合 D)。动作 a 可执行当且仅当：

```text
a.id 不在 D
并且 requires_all 是 I 的子集
并且 consumes 是 I 的子集
并且 requires_any 为空或与 I 有交集
```

执行后的事实为 `(I - consumes) ∪ produces`，执行集合加入 `a.id`。同一动作的消耗和产出不允许重合。未消耗的事实一直保留。每个动作只执行一次，包括寻找道具、对话和机关操作；如果真实行为可重复，不要默默按单次来建模。

目标全部同时存在即胜利。胜利状态不继续展开。可选内容在胜利之后才能执行，会被视为“通关前不可达”。`must_solve` 检查所有已找到的胜利状态，而不是把必做动作强行加入通关条件。

## 实体与线上映射

| 真实概念 | 模型写法 | 注意 |
|---|---|---|
| 可重复使用的钥匙 | requires_all 有 key，consumes 没有 key | 不自动模拟钥匙所在位置 |
| 一次性电池 | consumes 包含 battery | 电量和数量未建模 |
| 已知密码 | produces 包含 knows_code | 应区分纸条道具与玩家已记住的信息 |
| 打开房间权限 | produces 包含 room_open | 不模拟移动、距离、阻挡 |
| 在线登录 | produces 包含 logged_in | 不检查真正的认证实现 |
| 两条替代解法 | requires_any 包含两种条件 | 嵌套 OR-of-AND 应拆成中间动作/事实 |

多个相同物品应在小模型中显式区分 `battery_a`、`battery_b`。这不等于支持数量库存。所有玩家共享一份库存；如果物品无法在玩家间传递，本模型不适用。

## 解读报告

- `complete`：是否穷尽全部可达状态。
- `solvable`：是否找到胜利路径；完整且没找到为 false，未完整且没找到为 null。
- `all_states_can_win`：完整搜索后，所有可达状态是否仍有办法到达胜利。未完整总是 null。
- `solution`：最短动作数通关序列；并非最短实际时间。未找到为 null。
- `trace`：问题状态的最短动作数到达路径。重放时按顺序执行，再对照 `inventory`。
- `states`：已发现并存储的状态数；不完整时包括尚未展开的状态。
- `transitions`：已存储的可执行转移数。

依赖环不是一律错误：如果环有初始可用条件或替代入口，仍可能正常通关。因此本工具以实际可达性判定，不用“有环”替代“无解”。

检查结果只针对所输入的规则。遗漏“玩家能直接猜密码开门”等动作，会漏掉绕过；忘记补充真实备用电池，会误报软锁。试用时需要逐条把模型与设计资料对照。
